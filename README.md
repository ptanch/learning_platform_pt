# LMS (Learning management system) API — Django REST Framework

Этот проект создан в рамках изучения Django REST Framework (DRF).
Цель — разработать backend-часть LMS-системы, в которой пользователи могут размещать свои обучающие материалы: курсы и уроки.

Проект представляет собой REST API, возвращающий клиенту JSON-структуры, и используется как серверная часть для SPA-приложения.

## 📌 Функциональность проекта

На текущем этапе реализованы:

🔹 1. Подключение DRF

Создан новый Django-проект.
DRF подключён в settings.py через INSTALLED_APPS.

🔹 2. Модели

Созданы три основные сущности:
1. `User`
Модель размещена в приложении `users`.
Используется для хранения информации о пользователях системы.
2. `Course`
Размещена в приложении `lms`.
Отражает учебный курс.
Может содержать множество уроков.
3. `Lesson`
Также размещена в `lms`.
Связан с курсом отношением «один-ко-многим».
4. `Payments`
Размещена в приложении `users`.
Отражает платежную систему приложения

🔹 3. Расширение полей сериализаторов и вычисляемые поля

Добавлены кастомные поля, которые позволяют расширять выводимые данные без изменения самой модели.
Это особенно полезно, когда необходимо предоставить пользователю дополнительную информацию, например — статистику, агрегаты или сформированные данные.

🔹 4. Вложенные сериализаторы (множественный вывод)

Была реализована возможность одновременно выводить информацию о курсе и список всех его уроков.
Это позволяет формировать сложные структуры данных в одном запросе.

🔹 5. Настройка фильтрации и сортировки для платежей

Для эндпоинта `/users/payments/` добавлена возможность:

✔️ сортировать результаты по дате оплаты
✔️ фильтровать по:

- курсу (`paid_course`)
- уроку (`paid_lesson`)
- способу оплаты (`payment_method`)

Примеры запросов:

- Отсортировать по дате `?ordering=payment_date`
- В обратном порядке `?ordering=-payment_date`
- Фильтр по курсу `?paid_course=1`
- Фильтр по уроку `?paid_lesson=4`
- Фильтр по способу `?payment_method=cash`
- Комбинированный запрос `?paid_course=1&payment_method=transfer&ordering=-payment_date`

🔹 6. Кастомная валидация данных

Для полей уроков добавлена проверка через кастомный валидатор (`validate_video_url`).
Проверяется корректность данных и соблюдение правил заполнения.

🔹 7. Постраничный вывод (`pagination`)
Списки курсов и уроков теперь выводятся постранично через кастомный класс пагинации (`CustomPagination`).
Это делает работу с большими списками более удобной и позволяет подгружать данные по частям.

🔹 8. Тестирование
Все новые функции протестированы с использованием встроенного модуля `unittest`.
Проверяются права доступа, создание и обновление объектов, корректность постраничного вывода и подписки на курсы.

🔹 9. Настройка Celery для проекта

- Подключён Celery для асинхронного выполнения задач.
- Настроен брокер сообщений Redis и интеграция с Django.
- Поддержка таймзоны проекта для корректной работы периодических задач (`Europe/Moscow`).

🔹 10. Асинхронная рассылка писем пользователям
- Реализована Celery-задача `send_course_update_email`, которая отправляет письма подписчикам курса при обновлении материалов.
- Вызов задачи происходит в контроллере курса (`CourseViewSet`) после обновления курса.
- Отправка писем происходит **асинхронно**, не блокируя HTTP-запрос.
- Добавлена проверка частоты отправки: уведомления рассылаются только если с последнего письма прошло более 4 часов.

🔹 11. Периодическая задача для блокировки неактивных пользователей
- Создана Celery-задача `deactivate_inactive_users`, которая проверяет дату последнего входа (`last_login`) пользователей.
- Если пользователь не заходил более месяца, его аккаунт блокируется через флаг `is_active=False`.
- Задача выполняется **периодически** через Celery Beat согласно расписанию (например, каждый день в полночь).
- Расписание учитывает таймзону проекта для корректного запуска задач.

### 🔐 Авторизация и права доступа

**JWT-авторизация**

В проекте реализована JWT-аутентификация с использованием `rest_framework_simplejwt`.

Добавлены следующие эндпоинты:

- POST /users/token/refresh/ — обновление access токена по refresh
- POST /users/register/ — регистрация нового пользователя

Для доступа к защищённым эндпоинтам необходимо передавать заголовок:
```

```
Все эндпоинты проекта закрыты авторизацией — доступ к ресурсам возможен только после успешного входа.

### 👥 Роли и группы пользователей

Проект предусматривает разделение пользователей по ролям:

Группа "Модераторы"
Эта группа имеет расширенные права:
- могут просматривать любые курсы и уроки;
- могут редактировать любые курсы и уроки;
- не могут создавать новые объекты (Course, Lesson);
- не могут удалять объекты.

Права назначаются через Django Admin.

### 🛡 Права доступа и ограничения

В проекте настроена объектная логика доступа:

Для обычных пользователей

Пользователь может:
- просматривать только свои курсы и уроки;
- редактировать только свои курсы и уроки;
- создавать новые курсы и уроки;
- удалять только свои объекты.

Попытки обратиться к чужим данным приводят к ошибке авторизации.

Для модераторов

Модераторы могут:
- видеть и изменять все курсы и уроки независимо от владельца.

Но не могут:
- создавать новые курсы или уроки;
- удалять любые записи.

Такая логика заложена во `views.py` через кастомные разрешения (permissions), которые проверяют:

1. принадлежность пользователя к группе "модераторы";
2. совпадение владельца объекта и текущего пользователя.

## 📘 Документация API

В проект была подключена и настроена автоматическая генерация документации API.
Использованы следующие инструменты:

- `drf-yasg` — для генерации Swagger UI;
- `Redoc` — альтернативный интерфейс документации;
- `drf-spectacular` — современный генератор схем OpenAPI 3 (заменяет drf-yasg).

Документация доступна по следующим маршрутам:
- `/api/schema/swagger-ui/` — интерфейс `Swagger UI`
- `/api/schema/redoc/` — интерфейс `Redoc`
- `/api/schema/` — `OpenAPI JSON` схема (генерируется `drf-spectacular`)

Это позволяет удобно просматривать доступные эндпоинты и тестировать API во время разработки.

## 💳 Интеграция с Stripe

В проект добавлена возможность оплачивать курсы через платёжный сервис Stripe.
Реализация охватывает полный процесс подготовки данных и создания платежной сессии.

### 🔧 Сервисные функции (*services.py*)

Реализованы функции для взаимодействия с *API Stripe*:

1) Создание продукта
- Используется Stripe endpoint:
https://stripe.com/docs/api/products/create
- Функция создаёт продукт на основе данных курса.
- `product_id` сохраняется в модель `Course`.

2) Создание цены для продукта
- Stripe endpoint:
https://stripe.com/docs/api/prices/create
- Цена создаётся на основе стоимости курса.
- `price_id` сохраняется в модель `Course`.

3) Создание платёжной сессии
- Stripe endpoint:
https://stripe.com/docs/api/checkout/sessions/create
- На основе `price_id` создаётся checkout-сессия.
- Возвращаются `session_id` и `payment_url`.

### 🔧 Логика оплаты (*views.py*)

При создании объекта `Payment`:
1) Извлекается выбранный курс.
2) Для курса создаётся (или используется уже созданный) Stripe product и price.
3) Создаётся Stripe checkout session.
4) В модель `Payment` сохраняются:
- `stripe_session_id`
- `payment_url`
- статус устанавливается как `pending`.

В ответе клиенту возвращается JSON со всеми данными платежа, включая ссылку на оплату.

### 🔄 Процесс оплаты

1) Клиент создаёт платеж через POST-запрос на `/users/payments/create/`.
2) Сервер:
- создаёт продукт в Stripe (если ещё не создан),
- создаёт цену (если ещё нет),
- создаёт платёжную сессию,
- сохраняет все данные в Payment.
3) Клиент получает `payment_url` → переходит по ссылке → оплачивает курс.

## Настройка удаленного сервера и деплой

1. **Настройка сервера**
   - Создать виртуальную машину (Ubuntu)
   - Установить Python 3.12, Nginx, Git
   - Закрыть ненужные порты, оставить только 22, 80, 443
   - Настроить UFW (firewall) для безопасности
   - Установить и настроить Gunicorn с systemd (для автозапуска приложения)

2. **Настройка проекта**
   - Клонировать репозиторий
   - Перейти в ветку `feature/github_actions`
   - Создать виртуальное окружение и установить зависимости через Poetry:
     ```bash
     poetry install
     ```
   - Создать `.env` на основе `.env.example` и заполнить переменные окружения

3. **CI/CD через GitHub Actions**
   - Workflow запускается автоматически при push в ветку `feature/github_actions`
   - Шаги workflow:
     1. Устанавливает Python и Poetry
     2. Устанавливает зависимости проекта
     3. Запускает тесты проекта (`poetry run python manage.py test`)
     4. Если тесты успешны — деплой на сервер через SSH
   - Все чувствительные данные (секреты) вынесены в GitHub Secrets:
     - `SSH_HOST`, `SSH_USER`, `SSH_KEY`
     - `DJANGO_SECRET_KEY`
     - `ALLOWED_HOSTS` и другие переменные из `.env`

4. **Автодеплой**
   - Сервер автоматически обновляет код и перезапускает Gunicorn после успешного тестирования
   - Доступ к приложению осуществляется через Nginx на портах 80/443

## 🐳 Запуск проекта через Docker

Проект полностью контейнеризирован и запускается с помощью **Docker Compose**.
В составе проекта используются следующие сервисы:

- **web** — Django-приложение
- **db** — PostgreSQL
- **redis** — брокер сообщений
- **celery** — Celery worker для фоновых задач

### 📦 Требования

Перед запуском убедитесь, что у вас установлены:

- Docker
- Docker Compose

Проверить:
```
docker --version
docker compose version
```

### 🚀 Запуск проекта

1. Клонировать репозиторий:
```
git clone <repo_url>
cd learning_platform_pt
```

2. Создать файл `.env` (если его нет) на основе `.env.sample` и указать значения переменных окружения, например:
```
POSTGRES_DB=postgres_database
POSTGRES_USER=postgres
POSTGRES_PASSWORD=password

DB_HOST=db
DB_PORT=5432

REDIS_HOST=redis
REDIS_PORT=6379
```

3. Собрать и запустить проект:
```
docker compose up --build
```

После этого:

- автоматически применяются миграции
- поднимается Django-сервер
- запускается Celery worker

### 🌐 Доступ к сервисам

**Django-приложение**

- Адрес: http://localhost:8000
- Админ-панель: http://localhost:8000/admin
